# Product Architecture

## Objective
Enhance the native Splunk app version of the monitoring use case catalog with a deterministic engine that identifies direct and adjacent data sources already present in the Splunk instance and maps them to use cases.

## Product components

### 1. Catalog Experience
The existing use case catalog remains the primary browsing surface.

Enhancements:
- new filters based on discovery status
- mapping badges on use case cards and details views
- evidence drawer showing why a use case is considered direct, adjacent, partial, or unsupported
- launch point for environment scan

### 2. Environment Discovery Engine
A backend engine that inspects the Splunk instance and builds a local inventory of observable data assets.

Inventory dimensions:
- indexes
- sourcetypes
- sources
- hosts
- tags
- eventtypes
- CIM data model presence
- data model acceleration state
- field prevalence and field quality by sourcetype
- app / TA installation clues
- optional saved search, macro, and lookup clues

### 3. Deterministic Mapping Engine
A rules-based evaluator that compares discovered inventory against use case requirements.

Possible mapping states:
- direct
- adjacent
- partial
- none
- admin_asserted
- admin_rejected

### 4. Results Library
A persistent library that stores:
- discovered datasets
- mapping results
- scan history
- rule versions
- admin overrides
- exclusions
- manual mapping entries

### 5. Admin Refinement Workbench
A governance interface where admins can:
- confirm engine mappings
- reject false positives
- create explicit mappings
- define adjacency
- suppress noisy datasets
- attach notes and rationale

## User roles

### Admin
Full control over scans, mappings, overrides, and persistence.

### Power user / analyst
Can browse catalog and view evidence, but cannot change mappings unless granted permission.

### Read-only stakeholder
Can browse results and filters but cannot run scans or modify refinement state.

## Runtime boundary
The runtime feature must be implemented as native Splunk app functionality.

It must not depend on open-ended agent reasoning during user execution.

It may optionally use internally curated rulepacks generated by agentic processes during development, but runtime behavior must stay deterministic.

## Core design principles
- deterministic over heuristic
- bounded inspection over unlimited crawling
- explainability over opaque confidence
- admin governance over automated finality
- persistence over ephemeral UI-only results
- native feel over bolted-on tooling

## Product value
This feature turns the use case catalog from a static library into an environment-aware adoption accelerator.

It helps answer:
- Which use cases are already achievable in this environment?
- Which use cases are nearly achievable?
- Which data sources are missing?
- Which mappings are explicit vs inferred?
- What should be normalized next to unlock more value?
